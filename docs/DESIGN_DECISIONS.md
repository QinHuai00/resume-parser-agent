# 设计取舍记录

> 面试官问「为什么这么做」时，答案都在这里。每条都写：当时的选择、备选、拒绝理由、代价。

## 1. 输出约束：JSON Schema + 校验回灌 vs Function Calling

| | JSON Schema + 校验回灌（采用） | Function Calling 强约束 |
| --- | --- | --- |
| 跨厂商 | 只要兼容 `/chat/completions` 就行 | 各家 tools 支持程度不一 |
| 表达力 | 完整 JSON Schema（嵌套、约束、描述） | 普遍只有一层参数对象 |
| 可观测 | 校验错误原文直接进提示词 | 错误被框架吞掉，只剩「参数不对」 |
| 代价 | 模型可能不听 schema，需要修复环兜底 | 一次不听话就要整条重跑 |

结论：抽取类任务里「错在哪」比「错不错」更有价值，选可观测性。

## 2. 修复轮次：1 轮

`eval/results.md` 第三张表：100% 脏输入下，第 1 轮修复把结构合法率从 0 拉回 100%，
平均轮次 0.5；35% 脏输入下平均 0.08。第 2 轮只能救「模型连续两次犯不同错」这种少数情况，
而每次修复都是一次完整的长上下文调用。

- 默认 `max_repairs=1`；
- 参数暴露在 pipeline 与 CLI，业务侧可按「延迟预算 / 数据质量要求」调；
- 拒绝无限重试：会掩盖提示词或模型选型的问题。

## 3. 证据溯源：宁可为 null

模型编造字段在抽取任务里是**不可逆污染**：一条假手机号进了人才库，后续所有筛选、外呼、
去重都基于错误数据，且没人知道它是编的。

做法：`evidence` 要求每个字段给出原文逐字片段，匹配时先做归一化（去空白与标点、小写），
对不上就置 null 并记进 `dropped_fields`。

- 收益：precision 拉满，脏数据不进库；
- 代价：召回下降（评测里 phone 从「有值」变成 null，准确率 75%）；
- 为什么接受：把「未知」显式暴露给人工复核，比把「错误的确定」写进库里便宜得多。

## 4. 批量：异步任务 vs 同步循环

单份 1~3 秒；100 份同步处理 = 3 分钟起，worker 被占死，超时先挂。
所以 `POST /batch` 立刻返回 `task_id`，`asyncio.create_task` 后台跑，
`GET /tasks/{id}` 轮询进度。

- 并发用 `asyncio.Semaphore`（默认 4）：模型侧有 QPS 限制，并发开太大只会集体 429；
- 单份失败只标 failed，整批继续——批量任务最怕「一份坏文件毁掉全批」；
- 同步解析放到 `asyncio.to_thread`：httpx 是同步客户端，别阻塞事件循环。

## 5. 不引入编排框架

这条流水线的核心价值在控制流：校验、回灌内容、证据过滤、失败原因。
LangChain / LlamaIndex 会把重试与解析藏在内部，出问题时排查「这条为什么被丢」反而更难。
需要编排复杂化（多 Agent、多工具）时再引入——那时它带来的收益能覆盖调试成本。

## 6. 评测为什么用「注入故障的模拟模型」

真实模型评测需要 API key、有成本、结果随模型版本漂移，无法作为 CI 断言。
拆成两件事：

- **能力评测**（准确率）：用真实模型跑，数字自己报，仓库不预设；
- **工程评测**（修复环、证据过滤是否生效）：用确定性模拟模型 + 固定种子，
  可以进 CI，能在改代码时立刻发现语义回退。

这也是为什么 `eval/results.md` 里明确写着「mock 只证明修复环有效，不冒充模型能力」。
